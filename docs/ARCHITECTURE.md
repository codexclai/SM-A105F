# Architecture decision gate

The intended stack is necessary Samsung boot components → compatible Linux kernel and exact device tree → minimal initramfs → persistent Debian 13 `arm64` rootfs → CLI administration. This is a target architecture, not a verified boot design.

The immediate gate is kernel execution state. A 32-bit ARM kernel cannot directly run an AArch64 Debian userspace, even on a 64-bit capable SoC. A nearby recovery tree's `TARGET_ARCH=arm` is a userspace build declaration, not stock kernel evidence; Eureka's A105 build selects `ARCH=arm64`, but its compatibility with this stock firmware is unverified. Inspect the exact official Samsung release, stock boot image and device tree before choosing a kernel baseline or image format. If the stock path is ARM32, investigate a genuinely device-compatible ARM64 kernel and bootloader handoff; do not quietly switch the requested userspace to `armhf`.

At public Eureka commit `e1b8464bb29ce5bcb9d52bfcfc71bc2563e12563`, the root Makefile identifies a 4.4.302-p6 tree. Its A10 defconfig includes `CONFIG_CGROUPS`, `CONFIG_NAMESPACES`, `CONFIG_BLK_DEV_INITRD`, `CONFIG_CHARGER_S2MU005` and `CONFIG_MACH_EXYNOS7885_A10_OPEN`; the build script uses an A10-specific defconfig and a prebuilt A10 DTBO for packaging. The device tree declares ARMv8 cores and Samsung Exynos7885. These observations narrow the source comparison but do not establish the exact SM-A105F bootloader handoff, DTBO identity, Debian init compatibility, power safety or physical function. Do not execute the third-party build script without auditing its network fetches, destructive cleanup and submodules.

The custom A10 defconfig does not explicitly list every necessary feature, whereas the repository's `stock/a10_00_stock_defconfig` explicitly enables ELF execution, devtmpfs and ext4. This is not a comparison of generated `.config` files: Kconfig defaults and dependencies must be resolved in a complete checkout and the resulting config checked for Debian boot requirements before drawing conclusions about custom-kernel suitability.

Host Kconfig resolution of the pinned custom A10 defconfig on 2026-09-25 produced ARM64, ELF, ext4, initrd, namespaces and seccomp settings, but `# CONFIG_DEVTMPFS is not set`. The stock config had `CONFIG_DEVTMPFS=y`, but no stock correspondence to the user's firmware is established. [The experimental config generator](../scripts/configure-eureka-a10.sh) enabled only `DEVTMPFS` and `DEVTMPFS_MOUNT`; a second `olddefconfig` yielded exactly those two changed lines and a checksum recorded in [ARTIFACTS.md](ARTIFACTS.md). This addresses a host-visible early `/dev` prerequisite. It does not establish that this old Android-derived kernel boots Debian, meets security requirements or safely drives charging hardware.

Debian 13 ships systemd 257. Its [upstream v257 README](https://github.com/systemd/systemd/blob/v257/README) gives Linux 3.15 as minimum and 5.4 as recommended baseline; Eureka's 4.4.302-p6 falls between them. A pinned candidate Image and A10 DTB/DTBO set now compile on the host, but no systemd runtime test, QEMU boot or physical-device test occurred. The experimental config also enables `CONFIG_KSU=y`; that Android root integration is not justified for Debian and must be removed or explicitly reviewed before a Debian-oriented candidate. Investigate kernel APIs, cgroups, security maintenance, and userspace behavior before choosing a deployed baseline. A generated configuration or successful host build is not runtime compatibility evidence.

## Upstream LTS and user-namespace decision — 2026-09-26

The [kernel.org active releases page](https://www.kernel.org/) is dated 2026-02-25 in the evidence reviewed for this checkpoint. Its active longterm list is 6.18, 6.12, 6.6, 6.1, 5.15, and 5.10; Linux 4.4 is not listed. Therefore Eureka `4.4.302-p6` is not an active **upstream** LTS line as of that page. This is about upstream kernel.org maintenance only; it does not establish whether any downstream vendor or community fork receives separate maintenance.

The [upstream systemd v257.13 README](https://github.com/systemd/systemd/blob/v257.13/README) gives Linux 3.15 as its minimum and 5.4 as its recommended baseline. The 4.4 candidate is above the stated minimum and below the recommendation. This does not guarantee runtime compatibility: documented feature gaps and reduced support/testing remain, and no systemd runtime or guest-boot test has been performed.

The resolved candidate config `8cf0cdb2afd5dfcaff779460b09351cb6feeb4ebc306710598c2aeed6aae3d4c` leaves both `CONFIG_USER_NS` and `CONFIG_CGROUP_PIDS` unset and has `CONFIG_MEMCG=y`. With user namespaces disabled, services cannot obtain `PrivateUsers=` isolation through that mechanism. The upstream [kernel user-namespace resource-limit documentation](https://docs.kernel.org/admin-guide/sysctl/user.html) warns that enabling user namespaces can expose resource misuse and recommends memory cgroups for untrusted users; the [cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) describes the relevant resource-control interface. `CONFIG_MEMCG=y` alone does not prove that usable limits are mounted, configured, or enforced for the intended service model.

**Decision: unresolved; do not enable `CONFIG_USER_NS` automatically.** Before any enablement, verify the actual 4.4 implementation and limits for namespace creation and resource consumption, and establish that memory-cgroup controls are available and effectively applied to untrusted workloads. Otherwise retain the current setting and explicitly accept the missing `PrivateUsers=` isolation. Separately, `CONFIG_CGROUP_PIDS` remains unset and Linux 4.4 predates the systemd README's stated 4.5 baseline for its cgroup-v2 PIDs feature; that controller is unavailable in this candidate. No configuration or source change follows from this documentation review.

Next kernel work is to identify a supportable kernel/source path for the exact device and assess its boot correspondence and maintenance evidence; the active upstream LTS list is not itself proof that a newer line supports SM-A105F. Keep vendor-fork status distinct from upstream LTS status, and do not promote this host-built candidate toward deployment on these findings alone.


## Modern-kernel feasibility refresh — 2026-09-27

Primary upstream evidence confirms Linux has an Exynos 7885 SoC description and a board DTS for the Samsung Galaxy A8 2018 (SM-A530F), `exynos7885-jackpotlte.dts`, which includes `exynos7885.dtsi`. This is useful SoC-family support but is not an SM-A105F board port. No exact SM-A105F / Exynos 7884B board DTS was found in the checked upstream Linux tree. The distinction matters: the A10 device information in the Android `crDroid` A10 device tree describes a downstream Android device configuration, not a mainline Linux DTS or evidence that the A10 peripherals work with upstream drivers.

The current kernel.org longterm list identifies 6.18 and 6.12 among maintained lines, with projected EOL in December 2028. Use 6.18 as the first modern comparison baseline and 6.12 as a fallback comparison; this is a research starting point, not a final kernel choice. Exact A10 boot-chain compatibility, board DTS, peripheral coverage, firmware, and runtime validation remain absent. Next engineering step is to compare `exynos7885.dtsi` against the Eureka A10 SWA DTS and inventory, subsystem by subsystem, which A10 nodes can bind to upstream drivers versus requiring conversion, porting, firmware, or omission.

Sources checked: upstream [`exynos7885-jackpotlte.dts`](https://github.com/torvalds/linux/blob/master/arch/arm64/boot/dts/exynos/exynos7885-jackpotlte.dts); kernel.org [active releases](https://www.kernel.org/category/releases.html); secondary Android A10 device-tree notes at [crDroid](https://github.com/crdroidandroid/android_device_samsung_a10). The Android source is cited only for its claim that its Galaxy A10 target is Exynos 7884B, not as upstream kernel-support evidence.
